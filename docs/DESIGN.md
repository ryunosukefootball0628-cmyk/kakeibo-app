# 家計簿アプリ 設計書

## 1. 概要

家計簿 Web アプリ。日々の収支を記録し、カテゴリ別・支払い方法別に集計・グラフ化する。誰でも Google アカウントでログインして使え、記録はクラウド (Firebase) に保存して本人の端末間で同期する。

### 1.1 目的
- 収入・支出を簡単に記録できる
- カテゴリ別・支払い方法別の集計を見える化する
- クレジットカードなど支払い方法ごとの請求額を把握できる
- 定期支出・サブスクの管理により、固定費の見落としを防ぐ
- アルバイトなどのシフトを記録し、給料の見込みと実際の振込額を把握できる
- 銀行口座の残高と、カードの引き落とし・給料の振込を見込んだこの先の残高を把握できる

### 1.2 対象ユーザー
- 自分の家計簿をつけたい個人。複数の利用者がそれぞれのアカウントで使う
- 各利用者のデータは本人だけが読み書きできる。家族など複数人で 1 つの家計簿を共有する機能は対象外

## 2. 動作環境・技術スタック

| 項目 | 選定内容 | 理由 |
|---|---|---|
| 種別 | Web アプリ（SPA） | PC・スマホのブラウザで共通利用可能 |
| 言語 | TypeScript | 型安全性、保守性 |
| フレームワーク | React + Vite | 開発体験が良く、ビルドが高速 |
| スタイリング | 単一のグローバル CSS（CSS 変数によるテーマ） | 依存を増やさず、ライト/ダーク対応も容易 |
| データ保存 | Cloud Firestore（オフラインキャッシュ有効） | 端末間の同期、オフライン入力と再接続時の自動送信を SDK が担う。無料枠で小規模な利用は賄え、使われない期間があっても停止しない |
| 認証 | Firebase Authentication（Google ログイン） | パスワード管理が不要。Firestore のルールと uid で連携できる |
| グラフ描画 | Recharts | React との親和性が高い |
| ルーティング | React Router | 画面数が少ないため軽量に |
| 状態管理 | React Context + hooks（必要に応じて拡張） | 小規模なので外部ライブラリは最初は不要 |

※ 自前のサーバーは持たず、静的ホスティング + Firebase で構成する。手元へのバックアップ用に JSON エクスポート・インポート機能を用意する（後述）。

## 3. 機能要件

### 3.1 収支の記録・一覧（必須・優先度高）
- 収入／支出の登録（日付、金額、カテゴリ、支払い方法、メモ）
- 一覧表示（日付降順、月単位の絞り込み）
- 編集・削除
- 検索・フィルタ（カテゴリ、支払い方法、期間、キーワード）

### 3.2 カテゴリ別集計・グラフ（優先度高）
- 月単位でのカテゴリ別合計（円グラフ）
- 期間指定での月別推移（折れ線・棒グラフ）
- カテゴリは初期セットを用意しつつユーザーが追加・編集・削除可能
- カテゴリは収入・支出ごとにドラッグ＆ドロップで並べ替えられる。行の左端のつまみをマウスか指でつまんで動かす（つまみにフォーカスして ↑↓ キーでも動かせる）。HTML5 の drag and drop はスマホのタッチで動かないことが多いため、Pointer Events で実装する。並べた順は取引入力の選択肢や絞り込みにも使う
- 並べ替えるたびに、その種別のカテゴリへ 1 からの連番を振り直し、1 回の一括書き込みで保存する。他の端末での並べ替えがまだ届いていないなど手元の値が古いこともあるため、値が同じに見えるものも省かずに書く（省くと両方の並びが混ざる）
- 並べ替えの書き込みが画面に返ってくるまで（通常は数ミリ秒）は、次の並べ替えを受け付けない。続けて書くと、途中の書き込みの結果が返ってきた時点で表示が一つ前の並びに戻り、それをもとに次の並べ替えを計算してしまうため

### 3.3 支払い方法別集計・カード請求額確認（優先度高）
- 支払い方法（現金、銀行口座、クレジットカードA/Bなど）をユーザーが登録
- 支払い方法もカテゴリと同じ仕組み（3.2）でドラッグ＆ドロップで並べ替えられる。並べた順は取引入力・絞り込み・定期支出の選択肢と支払い方法別集計の並びに使い、先頭のものが取引を新しく入力するときの初期値になる
- 支払い方法別の月間合計を一覧表示
- クレジットカードは「締め日」「支払日」「支払いタイミング（当月／翌月／翌々月）」を設定でき、締め期間に基づいた請求予定額を算出・表示
- 請求額の算出ルール: ある支払月 P の締め月は `P - paymentMonthOffset`。対象期間は「締め月の前月の締め日の翌日」〜「締め月の締め日」。
  - 例1）15日締め・**翌月**27日払い（offset = 1）で 2026年11月の支払い → 対象期間 2026-09-16 〜 2026-10-15、支払日 2026-11-27
  - 例2）15日締め・**当月**27日払い（offset = 0）で 2026年10月の支払い → 対象期間 2026-09-16 〜 2026-10-15、支払日 2026-10-27
- 支払い方法別集計画面では、選択月から3ヶ月先までの請求予定額を一覧表示する
- クレジットカードには引き落とし口座（銀行口座）を設定でき、支払日に請求予定額をその口座の残高から引く（3.7）

### 3.4 定期支出・サブスク管理（優先度中）
- 定期支出（サブスク、家賃、保険など）をテンプレート登録（金額、カテゴリ、支払い方法、サイクル：毎月／毎年、発生日）
- 登録した定期支出を、対象月が来たら手動確認のうえ実績の取引として反映（自動生成候補を表示→ユーザーが承認して確定、の方式。意図しない重複登録を避けるため全自動登録は行わない）
- 定期支出の一覧・停止/再開・編集・削除

### 3.5 日別カレンダー（優先度中）
- 月単位のカレンダー（日曜始まり）に、日ごとの収入合計・支出合計を表示する
- 日付を選ぶと、その日の取引一覧と「この日に記録」ボタンを表示する。登録・編集の保存後はカレンダーの同じ月・同じ日に戻る
- 表示中の月と選択日は URL のクエリ（`?month=YYYY-MM&date=YYYY-MM-DD`）に持たせる。月・日の切り替えは履歴を置き換え、「戻る」で画面を抜けられるようにする
- マスの幅はサイドバーの有無で変わるため、カードの幅（コンテナクエリ）で金額表記を切り替える。狭いときは「1.2万」のような短い表記にし、正確な金額は日付を選んだ一覧で確認する

### 3.6 シフト・給与管理（優先度中）

アルバイトのシフト管理アプリ（シフトボードなど）のように、シフトを記録して給料の見込みを出し、実際に振り込まれた額を家計簿の収入として記録する。

#### 勤務先
- 勤務先（アルバイト先）を複数登録できる。名前、カレンダーでの色、締め日・給料日・給料が出る月（当月／翌月／翌々月）、深夜手当と残業手当の割増率を持つ
- 時給と交通費は「適用開始日」付きの設定として別に持つ（PayRate）。時給が変わったら、その日以降のシフトに新しい額を使い、それより前のシフトは当時の額で計算する。最低賃金の改定（毎年 10 月ごろ）や昇給で、過去の見込みが書き換わらないようにするため
  - 編集画面で時給・交通費を変えたら、「この日以降のシフトから」（日付を指定）か「これまでのシフトすべて」（入力の間違いを直す。履歴を 1 つにまとめる）を選ぶ。同じ適用開始日の設定があれば上書きする
  - 勤務先を作ったときの設定は「最初から」の意味で適用開始日を 2000-01-01 にする。作った日にすると、あとからそれより前の日付で時給の変更を入れたときに新旧が逆転するため
  - 最も古い設定は、その適用開始日より前のシフトにも使う（履歴から最初の設定を消した場合の扱い）
- 辞めた勤務先は「退職」にすると、シフトの入力先やテンプレートに出なくなる。過去のシフトと給料の記録は残る
- 勤務先を削除すると、そのシフト・テンプレート・時給の設定もまとめて消す（オンラインのときだけ）。記録済みの給料は家計簿の取引なので残す。勤務先は最後に消し、途中で失敗してもシフトだけが残って勤務先が見えなくなることがないようにする

#### シフト
- シフトは勤務先・日付・開始・終了（HH:MM）・休憩（分）・メモを持つ。終了が開始より前（または同じ）なら翌日の時刻とみなし、日をまたぐシフトも開始した日の分として扱う
- 月のカレンダーに勤務先の色でシフトを表示し、日付を選ぶとその日のシフト一覧と追加・編集・削除ができる。表示中の月と選択日は日別カレンダーと同じく URL のクエリに持たせる
- テンプレート（「早番 9:00〜17:00 休憩 60 分」など）を登録しておき、ワンタップで追加できる
- 「まとめて登録」では、カレンダーで複数の日を選び、テンプレートか時間を指定して一度に登録する（1 回の一括書き込み）
- 祝日はカレンダーで日曜と同じ色にする。祝日の判定は `src/utils/holidays.ts` が祝日法の決まり（春分・秋分の近似式、ハッピーマンデー、振替休日、国民の休日）から計算する。通信先を Firebase に限っているため外部の API は使わない。祝日法が改正されたらここを直す

#### 給料の計算（`src/utils/payroll.ts`）
- 時給はシフトの日付で決める。祝日の時給 → 土曜・日曜の時給 → 基本の時給の順に、設定のあるものを使う（日をまたいでも開始した日の時給）
- 深夜手当: 22:00〜翌 5:00 に働いた分に、時給 × 割増率を足す
- 残業手当: 勤務先・勤務日ごとに 8 時間を超えた分に、時給 × 割増率を足す。同じ日に複数のシフトがあれば開始の早い順に積み上げる。深夜と重なる分は両方の割増が付く（25% + 25% = 50%）
- 休憩は分数だけを記録するので、勤務時間の真ん中に取ったものとみなして深夜の時間を数える
- 交通費: 勤務先ごとに、出勤した日 1 日につき 1 日分を足す
- 金額は「時給 × 分 × 率(%)」の整数で積み上げ、基本給・深夜手当・残業手当をそれぞれ円に四捨五入してから合計する（内訳の合計と総額が一致するように）
- 給料日と対象期間は、カードの請求と同じ規則で求める（3.3 の算出ルール。`cycleForPaymentMonth` を共用）。例: 月末締め・翌月 25 日払いで 2026 年 11 月支給 → 対象 2026-10-01〜2026-10-31
- 所得税・社会保険料などの控除は計算しない。見込みは総支給額の概算で、画面にもそう書く

#### 給与画面と家計簿への記録
- 支給月ごとに、勤務先別の給料日・対象期間・出勤日数・勤務時間（深夜・残業）・内訳・見込み額と、対象期間のシフトを表示する
- 「給料を記録する」で、振り込まれた額（手取り）を収入の取引として記録する。定期支出と同じく自動では記録せず、利用者が額を確かめてから記録する（見込みと実際の額は控除などで違うため）
  - 取引には勤務先（`workplaceId`）と支給月（`payMonth`）を残し、見込みと突き合わせる。給与明細の総支給額（`grossPay`、任意）も残せる。総支給額があれば「総支給額 − 見込み」を、なければ「振込額 − 見込み」を差額として表示する
  - 入金日・額・カテゴリ・入金先は変えられる。カテゴリと入金先は、前回その勤務先の給料を記録したときのものを初期値にする（無ければ「給与」カテゴリと最初の銀行口座）
  - 記録した取引は取引一覧から編集・削除できる。編集しても勤務先と支給月の紐づけは残る
- ダッシュボードには、給料日を過ぎたのにまだ記録していない給料を表示し、給与画面の記録フォームへ案内する。給料日より前はシフトの変更で見込みが変わりうるので表示しない

### 3.7 口座残高（優先度中）

銀行口座の今日の残高と、来月末までの残高の見込みを確認する。銀行と連携して残高を取ってくるのではなく、利用者が確かめた残高に家計簿の記録を足し引きして求める（通信先を Firebase に限っているため、外部の API は使わない）。

#### 残高の求め方（`src/utils/balance.ts`）
- 銀行口座（種別が bank の支払い方法）に「残高を合わせた日（`balanceDate`）」と「その日の終わりの残高（`balance`）」を持つ。合わせた日までの入出金は残高に含まれているものとし、翌日からの次の入出金を足し引きする
  - この口座を支払い方法・入金先にした取引（収入は足し、支出は引く）
  - この口座を引き落とし口座にしたカードの請求額。支払日に、請求予定額（3.3 の対象期間に記録したカードの支出の合計）を引く。0 円の月は引き落としなし
- 今日の残高は、記録した取引とカードの引き落としだけから求める（給料などの見込みは入れない）
- 同じ日の入出金は入金を先に並べる。日の終わりの残高は順によらないが、日の途中で一時的にマイナスになったように見えないようにするため
- 通帳やアプリの残高とずれたら「残高を合わせる」で日付と残高を入れ直す。カードの請求額は概算なので、実際の請求額との差（締め日近くの利用の計上日のずれ、年会費など）や、記録できない ATM での引き出し・口座間の移動はここで吸収する。入力した日の、アプリで計算した残高との差も表示し、記録漏れに気づけるようにする
- 残高は 0 以上の整数とする（総合口座の貸越などのマイナスは扱わない）

#### 来月末までの見込み
- 今日の残高から、次を日付順に足し引きした残高を表示する。マイナスになる日があれば警告する
  - 今日より後の日付で記録した取引と、カードの引き落とし（締め日前の分は、そのときまでの利用額）
  - まだ記録していない給料の見込み（3.6 の見込み額。控除前）。振込先は、給与画面で記録するときの入金先の初期値と同じ口座（前回その勤務先の給料を記録した口座、無ければ最初の銀行口座）
  - まだ記録していない定期支出のうち、この口座から支払うもの
- 見込みは前月・今月・来月の分を探す。給料日・発生日を過ぎたのに記録していないものも、今日の残高に入っていないので先頭に「未記録」として並べ、記録への入口を付ける。ただし残高を合わせた日以前のものは、合わせた残高に含まれているので数えない

#### 読み込む取引
- 合わせた日の翌日から来月末まで。カードの請求額はそれより前の利用分から求めるので、合わせた日の月に支払う分の対象期間の初めから読む（その月の支払日が合わせた日以前なら 1 か月分余計に読むが、扱いを単純にする）。口座残高の画面では、定期支出を記録済みか確かめるため前月の初めからは必ず読む
- 合わせた日が古いほど読む件数が増える（無料枠の読み取りを使う）。ときどき残高を合わせれば少なく保てる
- 読み込む前の空の結果で計算すると誤った残高が出るため、支払い方法と取引の最初の結果が届くまで残高を表示しない

#### 画面
- ダッシュボードに、残高を入力した口座の今日の残高を表示する（選んだ月によらない）
- カードの引き落とし口座は支払い方法設定で選ぶ。新しいカードでは最初の銀行口座を初期値にする。引き落とし口座にしている銀行口座を削除すると、そのカードの設定も外す（1 回の一括書き込み）。設定が残っていても銀行口座でなくなっていれば未設定として扱う
- 取引の入力では、収入のときは「支払い方法」を「入金先」と表示する

### 3.8 アカウント・同期（優先度高）
- Google アカウントでログインする。未ログインではログイン画面だけを表示する
- ログインは同じタブで Google の画面へ移るリダイレクト方式にする。スマホではポップアップが別タブで開かれ、ログイン途中の情報が失われて失敗することがあるため（iPhone の Chrome で「missing initial state」を確認）。リダイレクト方式は中継ページ（`/__/auth/handler`）がアプリと同じドメインにないと動かないため、アプリを Firebase Hosting で配信する（8 章）。中継ページが別ドメインになる localhost での開発時だけポップアップ方式にする
- リダイレクトから戻ったときのエラーは `getRedirectResult` でしか受け取れないため、起動時に必ず呼んで画面に表示する
- 初回ログイン時に初期カテゴリ・支払い方法を作成する。2台で同時に初回ログインしても二重に作らないよう、トランザクションでプロフィールの有無を確かめてから作る
- 記録は同じアカウントでログインした端末間で同期する。他の端末での変更もリアルタイムに反映する
- オフラインでも閲覧・入力でき、接続が戻ると自動で送信する。画面操作からの書き込みはサーバーの応答を待たずに画面へ反映し、失敗はあとから画面上部に表示する
- ログアウト時は端末内のキャッシュも削除する（共用 PC で次の人に家計データを残さないため）。未送信の変更があれば警告する
- アカウント削除: 本人確認（Google の再ログイン）のあと、クラウド上の全データとアカウントを削除する。Firebase は削除に直近 5 分以内のログインを求めるため、データを消し始める前に ID トークンの `auth_time` で確かめる（データだけ消えてアカウントが残る事態を避ける）。リダイレクト方式の本人確認では画面が読み込み直されるので、戻ってきたことを sessionStorage の目印で判定し、最後の確認を表示する
- 旧バージョンで端末内（IndexedDB）だけに保存していた記録は、旧配信先（github.io）のオリジンにあり、新しい配信先からは読めない。旧配信先に置いた移転案内ページ（`moved/index.html`）が端末内の記録を見つけたら、移動せずに JSON での保存を案内し、新しい配信先でインポートしてもらう

### 3.9 更新のお知らせ
- 利用者から見える機能を変えたら、`src/updateNotes.ts` の先頭にお知らせを 1 件追加する（連番の `id`、公開日、変わった点）。内部だけの変更は載せない
- ログイン後、まだ見ていないお知らせをポップアップ（`<dialog>`）で表示する。「OK」・Esc キー・外側を押すと閉じ、見たことにする
- どこまで見たかは、見た中で最大の `id` を端末の localStorage に覚える。クラウドに置くとルールの変更と反映が要るため、端末ごとに 1 回ずつ表示されるのは許容する。localStorage が使えない環境では、開くたびに出るのを避けるため表示しない
- 次のお知らせは表示しない
  - 公開日より後に作ったアカウント（Firebase Authentication の作成日時で判定）。初めから新しい形で使っているため
  - 公開から 90 日を過ぎたもの。新しい端末で開いたときなどに、昔のお知らせまでまとめて出さないため

### 3.10 予算管理（任意・将来拡張）
- 今回のスコープ外。カテゴリ別の月間予算設定・超過警告は将来拡張として設計上の余地だけ残す（データモデルに budget テーブルを追加しやすい形にする）。

## 4. データモデル

Cloud Firestore に、利用者ごとに次の配置で保存する。ドキュメント ID がそのまま各レコードの `id` になる（ドキュメント内には `id` を持たない）。

```
users/{uid}                          プロフィール（createdAt のみ。初期データ作成済みの目印）
users/{uid}/transactions/{id}        Transaction
users/{uid}/categories/{id}          Category
users/{uid}/paymentMethods/{id}      PaymentMethod
users/{uid}/recurringExpenses/{id}   RecurringExpense
users/{uid}/workplaces/{id}          Workplace
users/{uid}/payRates/{id}            PayRate
users/{uid}/shifts/{id}              Shift
users/{uid}/shiftTemplates/{id}      ShiftTemplate
```

アクセス制御は `firestore.rules` で行う。

- `users/{uid}` 以下は `request.auth.uid == uid` の本人だけが読み書きできる。それ以外のパスはすべて拒否
- Google でログインしたアカウント（`sign_in_provider == 'google.com'`）に限る。コンソールで匿名ログインやメール／パスワードを誤って有効にしても、API キーだけで大量に作れるアカウントからは使えない
- 書き込みは下表の項目・型・範囲に一致するものだけを許可する（想定外の項目、負や小数の金額、巨大なメモなど）。保存する項目の一覧は `src/db/collections.ts` の `FIELDS` と揃える
- ルールは `npm run test:rules` でエミュレーター上のテスト（`tests/firestore.rules.test.mjs`）により検証する

クエリは単一項目の条件（`date` の範囲、`categoryId` の一致、取引の `payMonth` の範囲、シフトの `workplaceId` の一致など）だけを使い、並べ替えは画面側で行う。このため複合インデックスの設定は不要。

### スキーマのバージョン管理

クラウド移行前は端末内の IndexedDB（Dexie）に保存しており、そのスキーマを `version()` で管理していた。移転案内ページは Dexie を使わずに読むため、IndexedDB のバージョン（Dexie の値の 10 倍）から JSON の `version` を決める。

| DB version | 内容 |
|---|---|
| 1 | 初期スキーマ |
| 2 | `paymentMonthOffset` の基準を「翌月 = 0」から「当月 = 0」へ変更。既存のクレジットカードは値を +1 して従来の支払い月を維持する |

JSON バックアップにも同じ事情があるため `BackupData.version` を 2 に上げ、version 1 のファイルを取り込む際は同じ変換を行う。

シフト・給与の追加で `BackupData.version` を 3 に上げ、`workplaces` / `payRates` / `shifts` / `shiftTemplates` を含める。version 2 までのファイルにはこれらが無いので、取り込むと（全体を置き換えるため）勤務先とシフトは空になる。

口座残高の追加では、支払い方法に任意の項目（`debitAccountId` / `balanceDate` / `balance`）を足しただけで、それより前のファイルもそのまま読めるため `BackupData.version` は 3 のままにする（取り込むと残高と引き落とし口座は未設定になる）。

## 6.1 起動方法

```
npm install
npm run dev            # http://localhost:5173 (.env.local の Firebase につなぐ)
npm run dev:lan        # 同じ Wi-Fi のスマホから開けるよう LAN にも公開する (共用 Wi-Fi では使わない)
npm run emulators      # Firebase エミュレーターを起動 (Java が必要)
npm run dev:emulator   # エミュレーターにつないで起動 (Firebase の設定は不要)
npm run test:rules     # Firestore のルールをテスト
npm run build          # 型チェック + 本番ビルド
```

エミュレーターでも本番と同じリダイレクト方式でログインする（`src/firebase.ts` の `authDomain` を開いているホストにする）。エミュレーターのログインの中継ページ（`/emulator/auth/handler`）はリダイレクトの結果を自分のオリジンの sessionStorage に置き、アプリに埋め込んだ同じオリジンの iframe から読ませる。認証エミュレーター（`127.0.0.1:9099`）に直接つなぐとアプリと別オリジンになり、ブラウザのストレージ分離で iframe から読めずにログインが完了しない。そのため認証エミュレーターへの通信は Vite の開発サーバーが中継し（`vite.config.ts` の `server.proxy`）、アプリと同じオリジンから使う。Firestore のエミュレーターは `127.0.0.1:8080` に直接つなぐので、エミュレーターで試すときはこの PC のブラウザで開く。

## 7. 非機能要件

- データは利用者ごとに分けてクラウドに保存し、本人以外は読み書きできない（ルールで保証し、テストで確認する）
- 通信先は Firebase の API に限定する（CSP）
- オフラインでも入力でき、再接続時に自動で同期する
- 手元にも残せるよう、JSON エクスポート/インポートを提供する
- レスポンシブ対応（スマホ幅でも操作可能なレイアウト）
- 金額計算は浮動小数点誤差を避けるため、円単位の整数で保持する

## 8. デプロイ

Firebase Hosting で静的ホスティングする。`main` への push をトリガーに GitHub Actions（`.github/workflows/deploy.yml`）がビルドし、`dist` を Firebase Hosting へデプロイする。デプロイには `firebase init hosting:github` で作ったサービスアカウント（Secrets）を使う。

当初は GitHub Pages で配信していたが、アプリ（github.io）とログインの中継ページ（firebaseapp.com）が別ドメインになり、iPhone でログインに失敗したため移した。Firebase Hosting は `/__/auth/handler` を自動で配信するので、アプリと中継ページが同じドメインになる。

| 論点 | 対応 |
|---|---|
| 配信ドメイン | `https://kakeibo-pocket.web.app/` を正とする（authDomain と同じ）。プロジェクト ID から決まる既定のアドレス（`kakeibo-app-ea14f.firebaseapp.com`）は末尾にランダムな文字が付いて偽サイトのように見えるため、名前を選べるサイトを追加して移した |
| 別ドメインで開かれたとき | Firebase Hosting は 1 つのサイトを web.app と firebaseapp.com の両方で配信する。以前のアドレスのサイトにも同じアプリを公開しておき、authDomain 以外の Firebase Hosting のドメインで開かれたら起動時に authDomain へ移す（`src/main.tsx`）。中継ページが別ドメインになるとスマホでログインに失敗するため。以前のアドレスをサーバー側の転送（`firebase.json` の redirects）にしないのは、転送先の固定値とビルド時の authDomain がずれると転送がループするため |
| ルーティング | GitHub Pages で配信していた頃からの `HashRouter` のままにし、URL は `#/transactions` 形式とする。移転案内ページは `#` 以降を引き継いで移動する |
| 旧配信先 | GitHub Pages には移転案内（`moved/index.html`）を置く。移転先のデプロイが成功してから切り替える。移転先の URL はビルド時に Variables の authDomain から埋め込む |
| キャッシュ | `/assets/` はファイル名にハッシュが付くので 1 年キャッシュし、`index.html` とマニフェストは毎回確認させる（`firebase.json` の headers） |
| 公開範囲 | リポジトリは Public。公開されるのはソースコードのみで、家計簿のデータは Firestore にあるためリポジトリには含まれない |
| Firebase の設定値 | `apiKey` などはブラウザに配信される公開値だが、フォークした人が自分のプロジェクトに差し替えやすいようリポジトリには含めない。開発時は `.env.local`、Actions ではリポジトリの Variables（`FIREBASE_API_KEY` など）から渡す。未登録ならビルドを失敗させる |
| ログインできるドメイン | Firebase Authentication の「承認済みドメイン」に `<project>.firebaseapp.com` と localhost は最初から入っている。追加したサイトのドメインは、承認済みドメインと Google Cloud の OAuth クライアントの「承認済みのリダイレクト URI」（`https://<サイト名>.web.app/__/auth/handler`）に手で追加する。LAN のアドレス（スマホから `http://192.168.x.x:5173` で開く場合）は未登録のためログインできない |
| ルールの反映 | `firestore.rules` は自動では反映されない（GitHub Actions のサービスアカウントにはルールを変更する権限が無い）。変更したら `firebase deploy --only firestore:rules` で反映する |
| デプロイ用サービスアカウント | `firebase init hosting:github` は Hosting の管理者のほかに、Authentication の管理者（全利用者のメールアドレスの閲覧・削除ができる）や Cloud Functions の開発者などのロールも付ける。鍵が漏れたときの被害を Hosting に限るため、不要なロールは IAM で外す（README の「セキュリティのための設定」） |

### アイコン

`public/` に置き、ビルド時に base パス付きで配信される。デザインは配信アドレスの名前 (kakeibo-pocket) にちなみ、¥ の硬貨がポケットに入っている構図。配色はアプリに合わせ、地をアクセントの緑 (`#2f6f4f`)、ポケットを白、硬貨をダークモードのアクセント色 (`#7dbd99`) にしている。

| ファイル | 用途 |
|---|---|
| `favicon.svg` / `favicon.ico` | ブラウザのタブ。16px でも潰れないようポケットの縫い目を省いている。ICO は SVG 非対応ブラウザ向け (16px・32px を同梱) |
| `apple-touch-icon.png` | iOS のホーム画面 (180px)。iOS は透明部分を黒く塗るため角まで塗りつぶした正方形 |
| `icon-192.png` / `icon-512.png` | Android のホーム画面 (`manifest.webmanifest` から参照) |
| `icon-maskable-512.png` | ランチャーが丸などに切り抜く用。中心から半径 40% の安全領域に収まるよう図柄を縮小 |

マニフェストの `display` は `browser` にしている。`standalone` にすると、iOS ではホーム画面から起動したアプリが Safari と別の保存領域になり、ログインし直しが必要になる。さらにその中では Google ログインのポップアップが正しく戻らないことがあるため。

### セキュリティ方針

通信先を Firebase に限定する CSP をビルド時に `index.html` へ挿入し、ブラウザ側で他の宛先への通信を塞ぐ。依存パッケージに将来悪意のあるコードが混入しても、家計データを第三者へ送信できない。

- `connect-src`: Firestore（`firestore.googleapis.com`）と Authentication（`identitytoolkit.googleapis.com`, `securetoken.googleapis.com`）だけ
- `script-src` の `https://apis.google.com` と `frame-src` の認証ドメイン（`kakeibo-pocket.web.app`）: Google ログインの中継ページとのやり取りに Firebase が使う。認証ドメインはビルド時の設定値から埋め込む（本番では配信ドメインと同じ）
- `frame-ancestors 'self'` は meta タグでは指定できないため、Firebase Hosting のレスポンスヘッダーで指定する。`'none'` にしないのは、Firebase がログインの中継に同じドメインの `/__/auth/iframe` を埋め込むため
- 保存先のデータベースはアプリの管理者の Firebase プロジェクトなので、管理者は技術的にはデータを閲覧できる。ログイン画面と README でこの点を明示する

- `style-src` に `'unsafe-inline'` が必要: React と Recharts が `style` 属性を使うため
- CSP は本番ビルドにのみ適用する: 開発時は Vite の HMR が WebSocket を使うため（`vite.config.ts` の `apply: 'build'`）
- アカウント削除は、開発時の本人確認のポップアップをクリック直後に開く必要があるため `window.confirm` を挟まず、画面上の 2 段階のボタンで確認する。Google の再ログインが必要なので、誤操作だけでは実行されない

その他のレスポンスヘッダー（`firebase.json`）:

- `Referrer-Policy: strict-origin-when-cross-origin`: 他サイトへはオリジンだけを送る。`no-referrer` にしないのは、API キーに HTTP リファラーの制限をかけたとき、Firebase の API がリファラーでアクセス元を確かめるため
- `Permissions-Policy`: カメラ・マイク・位置情報・決済・USB を使わないので無効にする。依存パッケージが乗っ取られても、これらの許可を求められない
- `Cross-Origin-Opener-Policy` は付けない。Google ログインはアプリ → 中継ページ（`/__/auth/handler`、Firebase が配信するのでこちらのヘッダーは付かない）→ Google の画面と同じタブ内で移動し、途中の情報を sessionStorage で引き継ぐ。ブラウザによってはここで保存領域が切り替わり、iPhone でログインできなくなるおそれがあるため

依存パッケージとデプロイ経路（サプライチェーン）:

- `.npmrc` の `ignore-scripts=true` で、`npm install` / `npm ci` 時に依存パッケージのインストールスクリプトを実行しない。乗っ取られたパッケージが手元の `firebase login` の認証情報や Actions のシークレットを盗むのを防ぐ。今の依存（esbuild, protobufjs, @firebase/util）のスクリプトは無くても動く
- GitHub Actions の外部 Action はコミット SHA で固定し、デプロイ時に使う firebase-tools の版も固定する（既定は `latest`）。サービスアカウントの鍵を扱うため、タグの付け替えや新しい版の乗っ取りで中身が差し替わらないようにする
- 手元で使う firebase-tools（`package.json` の scripts と README のコマンド）も、デプロイと同じ版に固定する。手元の CLI は `firebase login` の認証情報（全利用者のデータを読める管理者権限）を使って動くため、`@15` のような範囲指定だと、乗っ取られた新しい版が公開された直後の実行で認証情報を盗まれうる。Dependabot は scripts の中の版を更新しないので、版を上げるときは `package.json`・README・`deploy.yml` の 3 か所を手でそろえる
- 開発サーバーは既定でこの PC からの接続だけを受け付ける（`vite.config.ts` で `server.host` を指定しない）。LAN に公開すると同じネットワークの誰からでも開け、Vite の「外部公開時に PC 内のファイルを読まれる」種類の脆弱性（2025 年に複数件）が見つかったときに上の認証情報を読まれるおそれがある。スマホで確かめるときだけ `npm run dev:lan` を使う
- 入力欄には firestore.rules と同じ上限（名称 100 文字、メモ 1000 文字、金額 1 兆円）を付ける。書き込みはサーバーの応答を待たないため、上限を超えると保存できたように見えたあと拒否されて記録が消える
- ワークフローの既定の権限は `permissions: {}` とし、各ジョブに必要な分だけ与える。`actions/checkout` は `persist-credentials: false` で GITHUB_TOKEN を作業ツリーに残さない
- Dependabot（`.github/dependabot.yml`）が npm と Actions の更新を週 1 回 PR で知らせる。公開直後の版は乗っ取りに気づかれる前のことがあるので、7 日待ってから提案させる
- `@grpc/grpc-js` は `package.json` の `overrides` で修正済みの 1.13 系に上げている。Firebase（`@firebase/firestore`）は最新版でも `~1.9.0` に固定していて、1.9 系には GHSA-m9gg-hp2v-232j・GHSA-f596-whhp-79r4（どちらも Node.js で動く gRPC サーバー向けの問題）の修正が出ていないため。ブラウザ版の Firestore は gRPC を使わず（指定の前後でビルド結果は同じ）、Node.js で使うのはルールのテストだけなので、配信するアプリには元から影響しない。Firebase が修正済みの版を使うようになったら `overrides` を外す

無料枠を使い切る悪用への備え:

- 誰でもログインできるため、悪意のある利用者が自分のアカウントから大量に書き込むと、Spark プランの 1 日の無料枠（書き込み 2 万回など）を使い切り、その日は全員が使えなくなる。ルールで 1 件の項目と大きさは制限しているが、回数は制限できない
- 無料枠は翌日（太平洋時間の 0 時ごろ）に戻る。再発は該当アカウントを Authentication で無効にして防ぐ（README の「悪用されたときの対処」）。削除ではなく無効にするのは、削除すると同じ Google アカウントで入り直せるため
- Firebase App Check（reCAPTCHA Enterprise。v3 は Firebase が Enterprise への移行を勧めている）でアプリ以外からのアクセスを拒否する案は、検討したうえで採用していない。理由は次のとおり
  - 防げるのは、アプリの外のスクリプトから API を直接呼ぶアクセスだけ。ログインが必須なので、攻撃者は自分のアカウントで本物のアプリを開ける。開発者ツールから書き込んだり、App Check のトークン（有効期限まで使い回せる）をコピーしてスクリプトで使ったりすれば回避できる
  - 課金のないプロジェクトでは、reCAPTCHA の評価は月 1 万回までで、超えると翌月 1 日までエラーになる。トークンを更新するたびに 1 回と数える。App Check を適用した状態で超えると、全員が月末まで使えなくなる。利用者が増えた場合も、わざと使い切られた場合も同じ。守りたい障害（翌日に戻る）より重い
  - SDK（firebase 12.19）は、reCAPTCHA のスクリプトを読み込めないとトークンの取得をいつまでも待つ。Authentication もその完了を待ってから通信する。そのため広告ブロッカーなどで reCAPTCHA が読み込めない環境では、ログインも起動時の認証も止まる（適用前でも同じ）
  - すべての画面で reCAPTCHA が動き、操作や端末の情報が Google に送られる。CSP で Google のスクリプトとフレームを許可することになり、「通信先は Firebase の API だけ」の方針から外れる
  - iCloud プライベートリレーや VPN を使う利用者は reCAPTCHA の点数が低く出やすく、適用後に弾かれるおそれがある
- 見直す条件: 別のアカウントで悪用が繰り返される／Blaze プランにする（reCAPTCHA の超過分が利用停止ではなく課金になる）／SDK が reCAPTCHA を読み込めないときにトークンの取得を打ち切るようになる

### データ消失対策

データはクラウドにあるため、ブラウザのデータ消去や端末の故障では失われない。残るリスクと対応は次のとおり。

- 未送信の書き込み: オフライン中の変更は端末内にだけある。ログアウト時に未送信の変更が残っていれば警告する
- まとめて書き換える操作（インポート・初期化・旧データ取り込み）: Firestore の一括書き込みは 500 件ずつに分かれ、途中で失敗しうる。先に新しい内容を書き込み、そのあと不要な記録を消す順にして、途中で止まっても記録が消えたままにならないようにする。オフラインでは開始しない
- 一覧の取得はキャッシュに一部しか無いことがあるため、エクスポートと一括操作は必ずサーバーから全件を読む
